# Demo narration script — 2:45, judge-facing

Companion to `walkthrough-2026-10-02.webm` (silent, 1.35 MB, recorded against the live product). This
file is the script and the storyboard: what is on screen, what to say, and the caption to burn in.
Beats marked **RE-SHOOT** are not in the existing capture and have to be recorded, because they are
the ones that carry the proof.

## Before recording

1. `npm run preflight` — refreshes every generated record, so nothing on screen is stale.
2. `npm run check:deployed && npm run check:settlement` — the two reads quoted in the last beat.
3. Two windows side by side: browser at 1440×900 with the product open, and a terminal with a large
   font, cwd `arb-guardian`, no secrets visible in scrollback.
4. Have these four explorer pages already loaded in tabs: the allowed spend, the refused spend, the
   drill's pause, and the drill's refusal-while-frozen. Do not type URLs on camera.
5. Run the drill **once** before recording so the pause/unpause gas is already paid and you know the
   timings are ~30 s; then run it again on camera, live.

## Beats

### 0:00–0:20 — The problem, and why a multisig is not the answer

**On screen:** the landing page headline, "Know before money moves."
**Say:** "Teams now give software permission to spend: a payroll bot, a keeper, an AI agent. A multisig
does not solve that. It bounds *who signs*, not *what can be spent* — a delegated agent holding a key
is still unlimited." 
**Caption:** `A multisig bounds who signs. It does not bound what a delegated agent can spend.`

### 0:20–0:40 — What this is, in one sentence

**On screen:** "Open workspace" → Overview.
**Say:** "Arb Guardian puts the policy inside the treasury's own execution path. An unsafe payment
does not get signed late and reviewed — it gets refused before it runs."
**Caption:** `Policy enforced inside Safe execTransaction. Not at the signer.`

### 0:40–1:05 — The policy, read from the chain (RE-SHOOT: evidence screen, lane card)

**On screen:** the Evidence tab, settlement-token cards, showing
`Lane configured · 5,000 USDG/day cap · recipient allowlisted · unpaused`.
**Say:** "This is USDG on both lanes. The cap is a thousand-times-a-condition claim about someone
else's contract, so the site reads it back from the chain instead of quoting it: registered, capped,
recipient allowlisted, unpaused. `npm run check:settlement` fails the build if any of that stops being
true."
**Caption:** `Read from PolicyManager, not typed by hand. 6 decimals — a wei-shaped cap would be wrong by 10^12.`

### 1:05–1:45 — Review a payment (in the existing capture)

**On screen:** Review tab → the pending request (1 ETH, unlisted address, 0.5 ETH day limit) → "Why
this decision".
**Say:** "A delegate asks for permission to pull money from the treasury. Three rules fire:
destination not allowlisted, daily limit exceeded, and a standing approval, which is refused
outright — an approval is exercisable later, outside the cap accounting. Blocked."
**Caption:** `Blocked. Deterministic rules, rule IDs, no model in the loop.`

### 1:45–2:10 — Refused on chain (RE-SHOOT: explorer tabs)

**On screen:** the allowed spend transaction (status 1), then the refused one (status 0), side by side.
**Say:** "Same treasury, same guard. The allowed payment settles. The unsafe one is a real transaction
that reverts *inside the Safe* — status zero, ninety thousand gas, no logs. That distinction is the
whole product: refused before execution, not reported after."
**Caption:** `Status 0 · reverted by SafeTreasuryGuard inside execTransaction.`

### 2:10–2:35 — The freeze, executed (RE-SHOOT: terminal, then explorer)

**On screen:** terminal, `npm run drill:incident:sepolia`, then the pause and refusal tabs.
**Say:** "Freezing is not a dashboard state. A risky request is refused in under two seconds, the
operator's mitigate step pauses the policy on chain in six, and the payment that normally settles is
now refused — then unpaused, and it settles again. Thirty-four seconds end to end, and the lane is
never left frozen."
**Caption:** `1.6 s to refuse · 5.8 s to freeze on chain · same spend refused while frozen · unpaused in finally`

### 2:35–2:45 — What is proven, and what is not

**On screen:** Evidence tab, judge path list, scrolled to source publication.
**Say:** "Six of six contracts recompiled to an exact match on Sourcify, verified panels on both
chains, no bytecode drift, 128 tests. Arbiscan's own panel is still pending a key, there is no
third-party audit, and no pilot users yet. That is what is true today."
**Caption:** `6/6 Sourcify exact match · 6/6 drift checks · Arbiscan panel pending key · no audit, no pilots`

## Delivery notes

- Read the numbers as they appear on screen; every one of them is generated by a command, so a stale
  number means `npm run preflight` was skipped.
- Do not say "verified on Arbiscan". The honest phrasing is "published on Sourcify with a verified
  Blockscout panel"; Arbiscan's panel is what is missing.
- Do not imply the USDG lane has moved money. It has not: the treasury holds 0 USDG and the issuer's
  testnet faucet refuses this machine's location.
- If a beat fails live (RPC lag, a rate limit), stop, say what failed, re-run it. A recorded failure
  explained on camera is worth more than a suspiciously clean take.
